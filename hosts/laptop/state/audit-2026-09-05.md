# laptop full audit -- 2026-09-05

Native boot, ~30 min uptime at time of audit (systemd PID 1, root on `LFSROOT`
nvme0n1p1, confirmed via `findmnt`/`lsblk`). `host.toml`'s own disk-layout note
still describes the pre-deploy plan (Gentoo root, deploy target not yet
reformatted) -- that text is stale; the deploy has completed since it was
written. First full audit since 2026-09-03 (post-boot spot-check); diffed
against that report below.

## Critical

- **91 of 211 tracked LFS/BLFS 13.0 advisories affect installed packages; 17
  Critical, 40 High** (`bin/lfsmaint --root / advisories`). Same finding as
  2026-09-03 ("never triaged"), still open two days later. Critical-rated:
  vim, perl, xz, python (x2), xml-parser, inetutils, linux (x2), glibc,
  gnutls, firefox, sshfs, util-linux, libssh2, libinput. Not something to
  patch in one sitting, but worth a deliberate triage pass given the count.

## Worth doing

- **Crash backlog since 2026-09-04, root cause not found.** 52 coredumps on
  disk (`coredumpctl list`). Two clusters worth root-causing, neither
  recurred on the current (09-05) boot:
  - `at-spi-bus-launcher` (SIGTRAP) and `wofi` (SIGABRT) crashed together
    ~38 times across a 3.5-hour window on 2026-09-04 morning (07:11-10:38),
    in lockstep -- every wofi crash paired with an at-spi-bus-launcher crash
    moments earlier. Points at the GTK accessibility-bus bridge under
    Hyprland's D-Bus session, not wofi itself.
  - `Hyprland` crashed 4 times in 5 seconds on 2026-09-03 evening (20:13:01-
    20:13:06), separate incident, also not recurred since.
  - Also present, one-off, not clustered: `Xwayland` (09-03), `slack`,
    `imv` x2, `firefox`, `emacs-30.2` (all 09-04 afternoon/evening) -- look
    like ordinary application crashes, not a pattern.
  - `coredumpctl --vacuum-time=<N>d` clears the backlog once reviewed;
    offered, not run.

- **Untracked, un-repo'd user unit fails twice at every boot.**
  `~/.config/systemd/user/track-odds.service` (a personal script, not part
  of this repo -- `grep -rl track-odds` over the tree found nothing) has
  `WorkingDirectory=/mnt/crypt/john/nextcloud/repos/sports` with no
  dependency on the crypt mount. It CHDIR-fails twice at boot
  (`journalctl -b`: 11:39:08, 11:39:40) before `RestartSec=30` lets it
  succeed once `/mnt/crypt` is up (11:40:10), and it's been running fine
  since. Cosmetic boot-log noise, not a project concern -- fixable with
  `RequiresMountsFor=/mnt/crypt` if desired. A stale duplicate of the same
  unit also sits under `~/old_home/.config/systemd/user/`, unused.

- **Continuous martian-packet flood, ongoing.** `IPv4: martian destination
  0.0.0.0 from 192.168.0.168, dev eth0` -- 430+ occurrences in this boot
  alone (`journalctl -p warning -b`), roughly one every 1-2 seconds,
  still arriving at the time of this audit. Source is another host on the
  192.168.0.0/24 LAN (`.168`), not this machine -- `arp`/`ip neigh` couldn't
  resolve it (no ARP entry cached, `arp` command itself not installed on
  this host). Worth identifying what `.168` is; it's flooding this host's
  kernel log continuously either way.

- **GDS still unmitigated after the microcode fix that resolved
  `old_microcode`.** `host.toml`'s previously-flagged `old_microcode`
  vulnerability is gone: `dmesg` confirms an early-load initrd updates
  microcode from 0xc6 to 0xf0 before the kernel checks, and `bugs:` in
  `/proc/cpuinfo` no longer lists `old_microcode`. But `dmesg` separately
  shows `GDS: Vulnerable: No microcode` -- this CPU's Gather Data Sampling
  mitigation needs a microcode revision beyond what 0xf0 provides. Worth a
  deliberate recorded decision the same way the rest of the microcode gap
  was (accept the risk, or track for a future microcode-package bump).
  **`host.toml`'s hw.microcode line is now stale and should be updated** --
  it still describes the resolved 0xc6/old_microcode state as open.

- **1394 uncompressed man pages + 14 uncompressed info pages**, up from the
  1087+9 the 2026-09-03 remediation compressed -- accumulated from packages
  built since (qt6, ffmpeg, libjxl, emacs, node per `BUILD-REPORT.md`).
  Safe, mechanical, not run:
  `find /usr/share/man -name '*.[1-9]' ! -name '*.gz' -exec gzip -9 {} \;`
  and the same for `/usr/share/info`.

- **`/mnt/crypt` (this repo's own filesystem) at 89%, 20G free of 169G.**
  Almost entirely personal data, not project files: `web_server` 63G, `vid`
  29G, `nextcloud` 24G, `old_home` 12G (a stale pre-migration home-dir copy).
  Not a project cleanup candidate on its own judgment, but worth being aware
  of before the next large rebuild -- `BUILD-REPORT.md` already names qt6 as
  this host's single most expensive rebuild class, and it shares this same
  volume.

## FYI

- **Bluetooth and camera drivers, unbound in the 09-03 audit, are now both
  bound** (`btusb`, `uvcvideo` in `lsusb -t`) -- that kernel-config gap has
  been closed since. SD card reader (RTS525A) and the Validity VFS7500
  fingerprint sensor remain without a driver/userspace support; both already
  known and deliberately deferred per `host.toml`.
- CPU governor is `powersave` on all 4 cores under `intel_pstate` active
  mode (HWP-driven) -- matches the deliberate, "believed correct, not
  re-benchmarked" decision recorded in the 09-03 remediation log. Not
  re-flagging.
- GPU genuinely uses the `iris` driver (no llvmpipe/swrast fallback); an
  Intel Vulkan ICD is registered; `ffmpeg -hwaccels` reports vaapi/drm/
  vulkan and `mpv.conf` sets `hwdec=vaapi`. `vainfo` isn't installed on this
  host, so VAAPI reaching the GPU end-to-end couldn't be independently
  confirmed -- the pieces are all in place.
- Storage scheduler is `none` on the NVMe device, `rotational=0` -- correct
  pairing, no spinning-disk default leaked through.
- 3539 binaries under `/usr/{bin,sbin,lib}` show as "not stripped" by
  `file`. Per the 09-03 finding: this book was never compiled with `-g`, so
  this is a symbol-table label, not real debug-info payload -- low value to
  act on, consistent with that prior conclusion.
- `lfsmaint verify`'s 16 "unexplained missing" are all previously-explained
  drift (dbus stale doc-path manifest; sudo/pulseaudio/systemd-networkd
  files absent by deliberate host choice -- NetworkManager instead of
  networkd, pipewire instead of pulseaudio) except gnome-keyring-48.0's 3
  "missing" files, which are actually tailscale's own log/state paths under
  `/var/lib/tailscale/` -- confirmed present via `lfsmaint owns`, just
  filed under the wrong package by whatever manifest capture ran. Files are
  fine; the manifest attribution is wrong. Low urgency.
- `/usr/lib/slack/chrome-sandbox` is the one SUID-root binary this audit
  can't trace to a tracked package -- expected, since Slack is a manually
  installed third-party app outside `lfsmaint`'s database, not a project
  package. Flagged for visibility per the skill's own convention, not
  because it looks wrong.
- Boot is fast (8.41s total). `findmnt --verify`: 0 errors (the fstab
  `devtmpfs`/`devpts` ordering fix from 09-03 held); the 2 remaining
  warnings are the same permission-denied artifacts as before, not real.
  fstab `LABEL=` entries match `lsblk`'s actual labels/UUIDs. 3 timers, all
  scheduled correctly, none stuck. 36 enabled units (no prior count to diff
  against this specific metric).
- Process table clean: no zombies, no `(deleted)` executables still
  running, all "duplicate cmdline" hits are legitimate multi-process
  components (kworkers, systemd worker pools, browser zygotes), every
  reparented-to-init process traces to an expected long-running daemon. No
  recurrence of the concurrent-build-driver bug class.
- No SUID/SGID binary is world-writable; no world-writable file or
  sticky-less world-writable directory found; no key material is group/
  other-readable; no non-root UID 0 account; no empty shadow password
  field. `iptables.service` is enabled and active; default-DROP policy on
  INPUT/FORWARD/OUTPUT, SSH explicitly allowed, tailscale's own chains
  (`ts-input`/`ts-forward`) wired in correctly -- confirmed with root
  privilege after the unprivileged `iptables -L` failed on the lock file
  (expected, not a finding).
