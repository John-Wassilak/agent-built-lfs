## Kernel config gaps found later the same day (2026-09-03, live Hyprland session)

Batch these into the next `hosts/laptop/kernel-config.sh` edit + rebuild -- not done
yet, deliberately deferred while a large Qt6 build (operator-requested, for
DankMaterialShell/Quickshell) has the machine's 2 build jobs and disk headroom
occupied. Confirmed directly against the running kernel's `/boot/config-$(uname -r)`
and `lsusb -t`, not guessed:

- **Bluetooth entirely absent.** `CONFIG_BT` is not set at all (not just the USB
  driver) -- Intel Bluetooth (`8087:0a2b`) shows `Driver=[none]` on both interfaces
  in `lsusb -t`. Needs `CONFIG_BT` + `CONFIG_BT_HCIBTUSB` (already flagged in the
  original hardware audit below as unbound, but not previously traced to the exact
  missing config symbols).
- **Integrated camera has no driver.** Chicony `04f2:b531`, `Driver=[none]`. Needs
  `CONFIG_USB_VIDEO_CLASS` (uvcvideo). Same pre-existing finding, now traced to the
  exact symbol.
- **No per-core temperature sensor**: `CONFIG_SENSORS_CORETEMP` is explicitly unset.
  Matches thermald's own "No coretemp sysfs found" log line exactly.
- **No power/energy capping framework**: `CONFIG_POWERCAP` is explicitly unset,
  which also blocks `CONFIG_INTEL_RAPL` (hard-depends on it) -- matches thermald's
  "NO RAPL sysfs present" line exactly. Note `CONFIG_PERF_EVENTS_INTEL_RAPL=y` is
  already on, but that's only `perf stat` energy counters, not the sysfs interface
  thermald/lm-sensors actually need.
- **Old microcode still vulnerable** (`host.toml`'s own already-flagged gap,
  unaddressed) -- not a `.config` toggle, needs an early-load initrd carrying
  updated Intel microcode, same pattern as server's `blfs-intel-microcode`.
- **SD card reader** (Realtek RTS525A, `rtsx_pci`) -- already known, deliberately
  deferred per `host.toml`, not a new finding, listed here only so the batch is
  complete if the operator wants it done in the same kernel rebuild pass.

**Not a kernel item, new hardware found and not yet tracked anywhere**: a Validity
VFS7500 fingerprint sensor (`138a:0090`) showed up in `lsusb`, not present in
`host.toml`'s `[hardware]` table at all. Kernel side is fine generically (USB HID,
already works) -- the real gap is userspace `libfprint` support, which is
notoriously spotty for this exact Validity model. A software/driver-support
decision for later, not something this kernel batch fixes.

Also worth doing in the same pass, from the original audit below, still open:

## Remediation log (same day, following user request "perform all tasks")

- **cpufreq-governor.service fixed** (Critical, above). `overlay/units/cpufreq-governor.service`
  rewritten to detect available governors instead of assuming `schedutil` exists, and to log
  what it did/found instead of masking failure with an unconditional `exit 0`. Applied to the
  live unit, `daemon-reload` + restart confirmed: it now correctly reports "no schedutil
  available ... leaving default (powersave)" instead of a silent write error. intel_pstate
  active-mode `powersave` is HWP-driven and already scales under load, so no further governor
  change was made -- this is believed correct, not benchmarked on this host specifically.
- **fstab ordering fixed** (Worth doing, above). `hosts/laptop/review-overrides.json`'s
  `ch10-fstab` block reordered (`devtmpfs` before `devpts`), recipe regenerated via
  `bin/extract-recipes.py --host laptop` (zero drift confirmed), applied to the live
  `/etc/fstab`. `findmnt --verify` now reports 0 errors (was 1 E, 2 W; the 2 W are
  permission-denied artifacts of running unprivileged, not real). **Server has the identical
  bug in its own `ch10-fstab` override, not fixed here -- out of scope, flagged for
  awareness.**
- **`/usr/lib/st*` unexplained files deleted** (Worth doing, above) -- `stC14zXr`, `st8DSbpl`,
  `st9kR9u4`. Root-privileged inspection during remediation identified them precisely: GNU
  `strip`/`objcopy`'s own temp-file naming convention (`st` + 6 random chars, unreadable,
  root-owned, executable) -- orphaned when a `strip` invocation crashed mid-operation during
  the *original* 2026-09-01 build (before its atomic rename completed). No process referenced
  them, not owned by any package, nothing else in the repo uses this naming pattern. Deleted
  per explicit instruction.
- **`sudoers.d/00-sudo` and dbus's 3 "missing" doc files: both false positives, not
  restored.** `sudoers.d/00-sudo` is present on disk (`-r--r-----`, correct content) --
  `john`'s earlier `ls: permission denied` was just non-root directory access, not absence;
  why `lfsmaint verify` flagged it is unresolved but the file itself is fine. dbus's 3 doc
  paths are the *same stale-manifest bug class CLAUDE.md already documents for
  lua5.4/lua5.5*: Chapter 8's LFS-stage dbus manifest recorded unversioned paths
  (`/usr/share/doc/dbus/...`), superseded by BLFS's `dbus-1.16.2` build writing the real,
  present files to versioned paths (`/usr/share/doc/dbus-1.16.2/...`). All 3 files exist;
  `ch08-dbus.txt`'s doc-path entries are simply stale and worth pruning at some point, not
  urgent.
- **Strip/compress hygiene (G) -- ran, caused real damage, partially reverted.** This
  build was never compiled with `-g` (confirmed: zero `.debug_*` sections on `bash`/`ls`/
  `gcc`, zero files under `/usr/bin`/`/usr/sbin` even touched by the strip loop) -- `file`'s
  "not stripped" wording refers to the symbol table, which `--strip-debug` deliberately
  never removes, so this entire class of finding was low-value from the start: there was
  essentially nothing to strip. Two `strip` invocations crashed with SIGBUS mid-run
  (matching the class that produced the original `/usr/lib/st*` files above); one of them
  **corrupted `/usr/lib/libsframe.so.3.0.0` to 0 bytes** because GNU strip falls back to
  in-place truncate-and-rewrite (unsafe) rather than its normal temp-file-then-atomic-rename
  swap in some cases, instead of leaving the original untouched. This is confirmed to have
  caused `systemd-udevd`'s one crash/auto-restart seen in the journal at 13:59:57 CDT (old
  PID 170 -> new PID 26517). **Restored from the intact chroot source
  (`/mnt/crypt/.../lfs/usr/lib/libsframe.so.3.0.0`)**, `ldconfig` refreshed, all binutils
  tools (`ld`/`objdump`/`readelf`/`nm`/`ar`/`strip`/`gprofng`) verified working. A full
  read-only ELF-validity sweep (`readelf -h` on every ELF under `/usr/bin`/`/usr/sbin`/
  `/usr/lib`) found no other corrupted binary. **The strip loop was not resumed/retried** --
  no further binaries were stripped after the crash; given there was nothing real to strip
  to begin with, this is not a loss. Man/info compression (the other half of G) *did* have
  real effect and completed cleanly on retry: 1087 man pages + 9 info pages, force-recompressed
  where a stale `.gz` existed from an earlier build predating a later package rebuild (matches
  the same "later rebuild leaves the manifest/cache behind" pattern as the dbus finding above);
  ~85 dangling man-page alias symlinks (`lzegrep.1 -> xzgrep.1`-style, xz/vim/coreutils
  multi-call conventions) were silently skipped as expected -- pre-existing, unrelated to this
  session. `findmnt --verify`, `systemctl --failed`, and a zero-byte sweep are all clean as of
  this remediation.
- **Not attempted: bluetooth (8087:0a2b) / camera (04f2:b531) kernel modules.** No Linux
  kernel source tree exists anywhere on this host or in the chroot volume -- building
  `btusb`/`uvcvideo` would mean fetching and reconfiguring the source from scratch, a
  materially larger and riskier undertaking than anything else in this pass, especially
  given today's proof that even routine hygiene operations can silently corrupt a live file
  on a system with no package manager to trivially recover from it. Deferred pending explicit
  go-ahead.
- **Not attempted: 87 packages with Critical/High advisories.** Not something to patch in
  one sitting; reported for triage, not acted on.

## Critical

- **cpufreq-governor.service reports success but did not set the governor.**
  `journalctl -b` shows four `echo: write error: Invalid argument` lines from
  the unit's `ExecStart`, one per core, immediately followed by "Finished" --
  the script ends with an unconditional `exit 0`, so systemd sees success.
  Live state: all four cores are on `powersave`, and
  `scaling_available_governors` on cpu0 lists only `performance powersave` --
  no `schedutil`. This CPU (i7-6600U) runs `intel_pstate` in active mode,
  which only exposes the two pstate pseudo-governors, not the generic
  cpufreq governor set the unit assumes (written for server's i5-2500K
  stack, where `schedutil` was measured and chosen -- see the unit's own
  comment citing the 2026-08-27 x264 finding). This is the same governor-
  pinning bug class that cost server a measured 2.1x loss, on a different
  code path. `intel_pstate` `powersave` does scale under load via HWP (not
  a hard pin like generic-cpufreq `powersave`), so the real-world severity
  is unmeasured, not zero -- worth a deliberate host decision (switch to
  `performance`, or set `intel_pstate=passive` to get `schedutil` back)
  recorded in `hosts/laptop/` the way the server governor decision was.

## Worth doing

- **`/etc/fstab` mount order**: `devpts` is listed before `devtmpfs` (`/dev`)
  in `hosts/laptop`'s fstab, but `/dev/pts` requires `/dev` to exist first.
  `findmnt --verify` flags it directly: `[E] wrong order: /dev/pts specified
  before /dev`. Fix is a two-line reorder in the fstab source (`ch10-fstab`
  per CLAUDE.md's convention) -- this is a real ordering defect, not
  cosmetic; the other two `findmnt --verify` warnings (permission-denied
  filesystem-type detection on `/` and `swap`) are artifacts of running
  unprivileged and not real findings.

- **Bluetooth and integrated camera have no bound driver.**
  `lsusb -t`: Intel Bluetooth (8087:0a2b) and Chicony Integrated Camera
  (04f2:b531) both show `Driver=[none]` on every interface. Needs
  `btusb` and `uvcvideo` kernel modules respectively -- neither is in
  `hosts/laptop/kernel-config.sh` yet per this audit; not previously
  flagged in `host.toml`'s `[hardware]` table the way the card reader and
  fingerprint sensor were. Genuinely missing, not intentionally deferred.

- **3 packages have unexplained missing files** (`lfsmaint verify`, 11 files
  total, none matching the compressed-after-install or ch08-cleanup
  patterns that account for the other ~11,070):
  - `dbus-1.16.2`: 3 doc/example files under `/usr/share/doc/dbus/`
  - `sudo-1.9.17p2`: `/etc/sudoers.d/00-sudo`
  - `systemd-259.1`: 7 files, mostly `network1`/`systemd-networkd` units
  Worth a manifest/recipe check -- `sudoers.d/00-sudo` missing in particular
  is worth confirming isn't masking a real default-sudoers gap.

- **Three unexplained files directly under `/usr/lib`**: `stC14zXr`,
  `st8DSbpl`, `st9kR9u4` -- all `root:root`, mode `750`-ish
  (`-rwx--x--x`, unreadable but executable), 250KB-1.5MB, all timestamped
  the same minute (2026-09-01 15:05, mid-build). Owned by no package per
  `lfsmaint orphans`. Naming matches a `mktemp` `stXXXXXX` template, not
  any legitimate install path -- grepped `recipes/` and `hosts/laptop/`
  for a `mktemp`-into-`/usr/lib` pattern and found none, so this isn't a
